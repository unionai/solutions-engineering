One model's journey, end to end

Hosts: Ray + Leon · ~60 min · recorded · builds on Sessions 1 & 2

Four stops. At each one, we hand the next a versioned Artifact, and every failure is recoverable.

Set the frame: today isn't a feature tour, it's a journey. We follow a single thing ("Review Radar", a product-review classifier) from a pile of raw text all the way to a URL someone can curl. Four stops: prepare, train, score, serve. The throughline is the Artifact: each stop produces a named, versioned output that the next stop picks up, so the whole path is traceable in the UI. And because things go wrong, we'll also show the safety net: rewind a failed run instead of restarting it. Everything runs live on the demo cluster; the deck is the map.
The path · one model, four stops

Follow the data, not the features

every arrow is a versioned Artifact · lineage in the UI, for free
Don't narrate the boxes: use them to plant the map. The key idea to land: the chapters are loosely coupled by Artifacts, not by code. Prep emits review-dataset; Train consumes it and emits review-classifier; Score and Serve both consume that same model. Stop 1 · a dataset you can trust

Label in parallel, and recover when it fails

Raw reviews, labeled in parallel, then checked before anything downstream uses them.

  • Micro-batching: split the corpus; a warm worker pool labels each batch, one action each.
  • @flyte.trace: the submit/poll calls are durable checkpoints: a retry resumes, it doesn't re-submit.
  • A quality gate fails the run after all that labeling: the expensive work is already done.
in: raw text→ hands off →review-dataset
▶ NOTEBOOK · 01_data_prep.ipynb: fan out labeling, fail the gate, then rerun --recover / fork: watch 8 batches land as RECOVERED.
This stop carries two lessons: scale and resilience. Scale: micro-batching + reusable workers label in parallel, and trace makes each external call a checkpoint. Resilience is the key point: run it, watch it fail at the quality gate after all the batches succeeded, which is exactly the case recover and fork are built for. Then: recover reuses the succeeded actions and re-runs only the gate; the UI literally shows the batches as RECOVERED. Fork is the same move when you've changed code (it rebuilds from your working tree). One-liner: recover = source run's code, fork = your code. Land that the dataset leaves as a versioned Artifact: the baton for stop 2.

Stop 2 · pick the best model

Find the best model, in parallel

Which hyperparameters give the best classifier? Evaluate the options in parallel.

  • HPO fan-out: every hyperparameter combo is its own action, launched together with asyncio.gather in a flyte.group.
  • Crown the winner by cross-validated score, then train it on the full set.
  • Stamp the model as the review-classifier Artifact: versioned, with its metrics attached.
in: review-dataset→ hands off →review-classifier
▶ NOTEBOOK · 02_training.ipynb: fan out the sweep, read the winner, train it, and publish the model Artifact.
Story: training is a race, not a single shot. Show the sweep fanning out (N trials, each its own action on a warm pool) then the driver picks the winner and trains the final model. The model leaves as an Artifact with its hyperparameters and accuracy as metadata, linked to the dataset version it came from. The scale-up beat matters for this audience: the tiny sklearn fit is a stand-in; the point is the task interface (inputs in, model Artifact out) is identical whether it's a 2-second fit or an 8-GPU FSDP job: you change resources and the training body, nothing else. Keep it to this one slide; the distributed detail is a reference note in the notebook.

Stop 3 · run it at scale

Run the model over a large corpus

Score far more reviews than fit on a single machine.

  • Fan-out / map: chunk the corpus, score chunks concurrently across a warm pool.
  • Shared DynamicBatcher: loaded once per replica, it aggregates records from all concurrent callers into cost-budgeted batches (the pattern that keeps a GPU full).
  • Consume the Artifact: point the job at review-classifier; out comes review-predictions.
in: review-classifier→ hands off →review-predictions
▶ NOTEBOOK · 03_batch_inference.ipynb: fan out scoring through a shared DynamicBatcher, publish the predictions Artifact.
Story: a trained model isn't doing anything until it runs at scale, which is what batch inference is for. The two ideas: fan-out (one action per chunk, warm pool) and load-once-per-replica (a process-level cache so you pay the model-load cost once, not per record). Make the GPU connection explicit: this is the exact structure you'd use to saturate an accelerator, just with a batcher in the cache slot. And note the lineage loop closing: predictions trace back through the model to the dataset. This is the shortest stop; keep momentum toward serving.

Stop 4 · serve the model

Serve it behind a live endpoint

The last stop: the model answers requests in real time.

  • Flyte Apps: a FastAPI endpoint and a Streamlit dashboard: any web app becomes a hosted, autoscaling service with its own URL.
  • Mount the Artifact: ArtifactValue("review-classifier") pins an exact version and Union injects it at startup: no bucket paths, no glue.
  • Scale to zero when idle; flyte serve to iterate, flyte deploy to ship.
in: review-classifier→ becomes →a live endpoint
▶ NOTEBOOK · 04_serving.ipynb: deploy the API, curl /predict, then the Streamlit dashboard: both mounting the same model.
The final stop: the model artifact from stop 2 becomes a callable service. Show the FastAPI app deploy, then curl /predict live: positive vs negative. The key platform point is the artifact mount: the app declares ArtifactValue("review-classifier") and Union resolves the version, downloads it, and injects it as a file at on_startup; there is no ambiguity about which model is serving. Mention scale-to-zero (cost) and serve-vs-deploy (iterate vs ship). If time allows, open the Streamlit dashboard for a click-through. Close the loop verbally: raw text entered at stop 1 is now a prediction from a URL.
