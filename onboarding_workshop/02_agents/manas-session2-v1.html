1 · Best practices

Testing, outputs & integration

The three questions you raised on Slack:

  • Testing: two ways to invoke a task in a test: call it directly to check the body (no cluster), or flyte.run for the serialized path. retries / timeout / cache recover from system errors.
  • Task outputs: typed and durably persisted; read them with run.outputs(), or query past runs anywhere via the flyte.remote API.
  • Integration: Flyte is just Python you call, so wrap it or use it directly.
Recover from system errors
cache="auto" + retries + timeout: transient failures heal themselves, no custom code.
Tolerate user errors
asyncio.gather(..., return_exceptions=True) skips a bad record instead of sinking the whole run.
Wrap, or use directly? Both.
Engineers use the CLI/SDK directly; internal tools wrap flyte.run() + flyte.remote for everyone else, with triggers to schedule and apps to serve.

2 · Agentic pipelines

Build a durable agent, step by step

Five steps
1 · a durable @flyte.trace LLM step → 2 · the tool loop by hand → 3 · the flyte.ai.agents.Agent harness → 4 · a parallel plan / fan-out / synthesize pipeline → 5 · serve or schedule it.
Two idioms, one substrate
Hand-roll the loop for full control, or let the Agent harness write it. Either way you get durable checkpointing, sandboxed isolation, parallel fan-out, and a traced span per step.

Why agents belong on Flyte:

  • Durability: typed, persisted artifacts, not in-memory scratchpads
  • Observability: every LLM & tool call is a span you can replay
  • Recovery: retries / timeouts absorb rate limits & blips
  • Fan-out: one agent per sub-topic, in parallel

Docs: Build an agent · Tracing

▶ NOTEBOOK · 02_agentic_pipeline.ipynb (+ 02_agentic_pipeline.py): a research agent that plans, fans out one agent per topic, and synthesizes on the cluster, with a report.
The big idea: most "agent" patterns are just tasks; reach for the Agent harness only where the model must choose tools. Build up live: start with one traced call so the dashboard span is concrete, then reveal that the harness is just the hand-rolled loop written for you. On the run page, point at the fan-out group, the per-agent actions, the traced tool calls, and the report tab.
3 · Agentic dev on Union

The Flyte agent plugin + MCP servers

Install it into your coding agent (Claude Code & Codex wire it up automatically). It grounds the agent in the Flyte SDK & docs, so it can:

  • Scaffold tasks, workflows, apps & agents, then build, ship & serve them
  • Run & inspect executions on your cluster
  • Migrate Flyte 1.x and Slurm jobs to Flyte 2
21 skills, 3 groups
Authoring (10): scaffold, types, ship, eval, optimize. Migration (6): Flyte 1.x & Slurm to Flyte 2. Deployment (3): EKS, kind.
Two MCP servers
flyte-docs: hosted search over the SDK docs & examples, no auth. flyte-cluster: 29 local control-plane tools to run, inspect logs, and manage runs, apps & secrets.

Docs: Agent plugins (skills + flyte-docs & flyte-cluster MCP)

▶ LIVE EXERCISE · 03_fix_broken_workflow.py: hand your agent this broken workflow and let it run, inspect the failed run, and fix it until green.
General overview of the plugin, then show it live. The pitch: it turns your coding agent into a Flyte development partner that is grounded, not guessing: it scaffolds correct 2.0 code, looks up real docs via flyte-docs, and runs and inspects on the cluster via flyte-cluster. Claude Code and Codex auto-wire both MCP servers; other harnesses (Hermes, opencode, pi) configure them manually. Land it with the broken-workflow exercise: fail, read the cluster log, fix, rerun, go green.
