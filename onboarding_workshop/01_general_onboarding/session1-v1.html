0 · Framing · Why Flyte

Your Python, made durable & distributed

The old way
SLURM scripts, notebooks, code on a VM. Parallelism is manual, failures are yours to babysit, and "what ran, on what, for how long?" is hard to answer.
With Flyte
Write normal Python. Each function becomes a containerized, reproducible job — parallel, retryable, and fully observable. Same code runs on your laptop or the cluster.

What that gets a research team:

  • Scale out experiments without writing scheduler glue
  • Reproducible runs — inputs, outputs, and code tracked
  • Right-size compute per step (CPU here, GPU there)
  • One place to see what ran and why it failed

Start here: union.ai/docs › Overview

Keep it short and momentum-focused. Read the room: who's on SLURM today, who's in notebooks, who's already running on Union. Framing: they're moving distributed training off SLURM and running drug-discovery pipelines — lead with "your Python, unchanged, but durable and parallel."

2 · Tasks & runs · example

What a task actually looks like


import flyte

env = flyte.TaskEnvironment(
    name="hello_union",
    resources=flyte.Resources(memory="250Mi"),
)

@env.task
def greet(name: str) -> str:
    return f"Hello, {name}!"

@env.task
def main(names: list[str] = ["Alice", "Bob"]) -> list[str]:
    return list(flyte.map(greet, names))   # runs in parallel
  • Plain Python + one decorator
  • main calls greet — that's a workflow
  • flyte.map fans it out in parallel

3 · Workflows & fan-out

Tasks calling tasks — in parallel

  • Fan out with flyte.map(), asyncio.gather, or flyte.group
  • Each invocation is its own action — hundreds run at once, each in its own pod
  • Handle failures per-item so one bad task doesn't sink the batch
Replaces the SLURM job array
Split → process in parallel → aggregate, in normal Python — no scheduler glue, no submit scripts.
Control the concurrency
Cap how many run at once — the built-in answer to licensing / API rate limits on third-party services.

Docs: union.ai/docs › Fanout · Controlling Parallelism

4 · Data & I/O

How data moves — automatically

Pass values like normal
Return a value from one task, use it in the next — Flyte offloads it to object storage and hands it back, transparently.
Big or file-based data
Use File, Dir, and DataFrame to move large artifacts by reference — no copying whole datasets around.
  • Small outputs: just return them
  • Files/models: File.from_local() → .download()
  • Structured inputs: dataclasses for typed, safe I/O

5 · Environments, images & resources

Right compute, right dependencies

  • Declare an image — from_debian_base().with_pip_packages(...)
  • Request resources per task — CPU, memory, GPU
  • Split heavy vs light work across environments; a driver depends_on its workers
  • Pull from your own registry
One size does not fit all
A CPU orchestrator can fan out to GPU workers — each task gets exactly the hardware it needs, nothing more.

6 · Best practices · Speed & cost

Faster iterations, lower spend

Reusable containers
Reuse a warm container across many tasks instead of cold-starting each one — big speedup for fan-out, and less wasted compute.
Caching
cache="auto" skips recompute when inputs haven't changed — don't pay to run the same step twice.

Docs: union.ai/docs › Reusable Containers · Caching

Direct hook to the team's cost / right-sizing focus (their tasks were over-provisioned 10x). Reusable containers + caching are the two biggest levers. Show the reuse speedup live on the fan-out if the demo env allows.
